# 生产入口收敛与迁移说明

> 适用版本：`python_agent` 2026-11 收敛之后（分支 `codex/durable-chat-turns`）。
> 本文是**当前契约**的权威描述；`README.md` 后半部分保留历史评测记录，涉及旧开关的
> 段落仅作留档。

## 1. 收敛前后改了什么

| 维度 | 收敛前 | 收敛后 |
|---|---|---|
| 服务缓存 | `agent/support/cutover._services` 与 `app.state.support_v2_service` **两份** | `app.state.support_runtime` **一份**（`app/services/support_runtime.py`） |
| 请求模型 | `app/schemas.ChatRequest`（无 `turn_id`）+ `entrypoint.ChatRequest`（有） | 只有 `app/schemas.ChatRequest` |
| 轮次 ID | 用 `X-Trace-Id` 顶替 | 请求体 `turn_id`；缺省按 `X-Trace-Id` 兼容；`answer_id == turn_id` |
| 走哪张图 | 请求体 `has_pending_ticket` 可单方面决定 | 服务端检查点**三态探测**：`pending → 409`、`unknown → 503`、`clear → 四 Agent`；新提问永不进旧图 |
| 模型来源 | 设了 `FOUR_AGENT_MODEL_NAME` 就全体租户换平台模型 | 默认用租户已验证配置；换模型需 `FOUR_AGENT_EVAL=on` |
| 开关 | `SUPPORT_AGENT_V2` / `FOUR_AGENT_GRAPH` / `X-Agent-Graph` 三处语义 | 全部退役；`cutover.enabled()` 退化为会抛 `RuntimeError` 的墓碑 |
| `/agent/chat/v2` | 代码里有、镜像里没挂载，且自带一份请求模型 | 已挂载（`app/api/chat_v2.py`），与 `/agent/chat` 同一实现、同一鉴权、同一请求模型 |
| 能力边界 | 主图直接 import `tools` / `retrieval` / `llm_config` / `faq_agent` | 经 `app/agent/capabilities/` 稳定接口 |
| 旧审批 | 恢复逻辑散在 `chat.py`；判定是布尔值，读失败等同"没有审批" | `app/agent/legacy_approval/`（三态判定 + 原键恢复）；读失败是 `unknown`，不是 `clear` |

## 2. 请求与响应契约

```http
POST /agent/chat          → AgentResp（JSON）
POST /agent/chat/stream   → SSE: progress* / chunk / end | interrupt | error
```

请求（`app/schemas.py::ChatRequest`）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `thread_id` | 是 | `{tenant_id}:{session}` 形式；与 `X-Tenant-Id` 必须一致 |
| `user_message` | 是 | 客户原话 |
| `turn_id` | 否 | 幂等键，`[A-Za-z0-9_.:-]{1,64}`。业务 Worker 每轮生成一次，重试复用 |
| `has_pending_ticket` | 否 | 业务层排队事实；只用于抑制重复转人工，**不决定走哪张图** |

响应（`AgentResp`）：`success` / `is_interrupt` / `interrupt_data` / `content` /
`trace_id` / `answer_id` / `turn_id` / `outcome` / `error_code` / `agents` / `evidence_ids`。

三条硬约束：

1. `answer_id == turn_id`，JSON 与 SSE 的 `end` 帧必须同值；
2. 同一 `turn_id` + 同一问题 = 重放（不调模型、不计费、不追加消息）；
   同一 `turn_id` + 不同问题 = **409**（`detail` 指明是 turn_id 冲突）；
3. SSE 的 `chunk` 与 `end` 携带同一份正文；`end` 另带 `outcome` / `agents` /
   `evidence_ids`，与 JSON 逐项相同。

`X-Trace-Id` 只做追踪：它进 trace，不参与幂等判定（除非客户端没给 `turn_id`，
此时按它兼容，行为与升级前一致）。

### 2.1 闸门冲突体（409 / 503）

三个生产入口共用 `app/api/approval_gate.py::require_clear`。冲突是**结构化**的，Worker
可以据此判断"该建单 / 该等 / 该重试"，而不是猜文本：

```json
{
  "error_code": "approval_pending",
  "thread_id": "t_demo:s1",
  "turn_id": "turn-7",
  "retryable": false,
  "resume_endpoint": "/agent/resume",
  "checkpoint_keys": ["support_v2:t_demo:s1", "t_demo:s1"],
  "pending_approval": { "action": "transfer_to_human", "reason": "等待人工确认" },
  "detail": "该会话有未完成的转人工审批，请走 /agent/resume"
}
```

| `error_code` | HTTP | `retryable` | 语义 |
|---|---|---|---|
| `approval_pending` | 409 | `false` | 旧图停在 `__interrupt__` 上；新提问被拦住，只能 `/agent/resume` |
| `approval_state_unknown` | 503 | `true` | **读检查点抛异常**；状态未知，本轮暂停，稍后重试 |

两者的区别是这次改造的重点：以前读失败被当成"没有审批"，会让旧审批与新图在同一个
会话里并行；现在是 `unknown`，宁可让 Worker 退避重试，也不放行。

SSE 入口的闸门在**建立流之前**执行，所以冲突是真正的 HTTP 409/503，而不是 200 流里
的一帧 `error`——客户端不需要解析流就能分流。

### 2.2 `/agent/resume` 与 `/agent/approval/{thread_id}` 的客户端契约

业务层不能用"拿到 content"判断恢复成功：`success=false`、503、超时都不会抛异常，
也不会带回正文。客户端必须把结果分成四类（实现见
`python_business/business/chat/recovery.py::ResumeOutcome`）：

| 结果 | 判定依据 | 业务动作 |
|---|---|---|
| `recovered` | 200 且 `success=true`（或超时后复查为 `clear`） | 结案，工单待办置 `done` |
| `clear` | 200 且 `error_code=no_pending_approval` | 本来就没有待审批，同样结案，**不要**再调 resume |
| `unknown` | 200 且 `error_code=approval_state_unknown`，或 HTTP 503 | 可重试：记待办，后台重试 |
| `unavailable` | 连接失败 / 超时 / 其他 5xx | 可重试；**必须先复查**，再决定是否 resume |

```http
GET /agent/approval/{thread_id}
→ {"thread_id": "...", "approval_state": "pending|clear|unknown", "checkpointer": true}
```

这个探测端点不查检查点表、不需要数据库连接池，专供业务层"重试前先问一次"。
超时后服务端可能已经恢复完成，复查到 `clear` 就直接结案——不再白跑一轮旧图。

## 3. 路由规则（唯一判定）

```python
state := approval_state(app, thread_id)      # pending / clear / unknown
state == PENDING -> 409 approval_pending     # 不跑任何图
state == UNKNOWN -> 503 approval_state_unknown（retryable）
state == CLEAR   -> 四 Agent 主图
```

* 判定不建图、不调模型：直接 `checkpointer.aget_tuple({"thread_id": thread_id})`，
  看有没有 `__interrupt__` 待写记录。
* **没有 checkpointer（如纯离线构造）才判 `clear`**；`aget_tuple` 抛异常一律 `unknown`。
  这两种"读不到"必须分开——前者是结构上不存在，后者是暂时读不到。
* 生产入口**不再有第二条通往旧图的路**：`_legacy_json_impl()` / `_legacy_stream()` 已删除，
  有源码级测试（`test_production_entry_never_calls_the_legacy_agent`）钉住
  `app/api/chat.py` 不得出现旧图调用。
* `/agent/resume` 是旧图的**唯一**入口：没有未完成审批返回
  `success=false, error_code=no_pending_approval`；探测异常返回
  `error_code=approval_state_unknown`（不再当成"没有审批"去按默认分支编答复）。

### 3.1 Business 侧的分流（先看业务状态，再叫 Agent）

`python_business/business/chat/worker.py` 按 `business/chat/routing.py::route_message`
的固定顺序分流，**业务状态在前、Agent 在后**：

| 序 | 条件 | 行为 |
|---|---|---|
| 1 | 消息已被人工接管（`handling_ticket` 命中） | 回"消息已转给人工客服"并把原话推给管理员，不调 Agent |
| 2 | 媒体消息（`msg_type != text`） | 固定媒体提示，不调 Agent |
| 3 | 客户明确要求转人工（`explicit_handoff`） | 建单/复用单 + 工单号提示，不调 Agent |
| 4 | **已有待处理工单**（`waiting_ticket` 命中） | 回"已提交人工客服（工单号：X），正在等待人工接入"，不建第二张单、不调 Agent |
| 5 | 其余 | 调用四 Agent；`approval_pending` → 建单/复用单 + `/agent/resume` + 本轮提交为 `ticket`；`approval_state_unknown` → 可重试基础设施错误 |

第 4 条是关键：`has_pending_ticket` 从此只是"业务在排队"的事实，**不再是选择旧 Agent
的开关**。第 5 条的 409 处理保证"Agent 返回 409 → Worker 重试三次 → 客户看到处理失败"
不会发生；503 走可重试的基础设施错误，不会把工单建重（`ensure_customer_ticket`
的 `FOR UPDATE` + `complete_turn` 的租约栅栏保证 `turn_id`、工单复用、轮次提交都幂等）。

两点边界要知道：

* `explicit_handoff` 是**整句**匹配（"转人工"/"我要转人工客服"命中；"我要真人客服"
  这种不带"转/接"动词的说法不命中，会交给 Agent）。这是刻意的：一旦放宽成"包含关键词"，
  "人工客服几点下班"就会被直接建单。
* 第 3 条排在"排队中"前面，所以已在排队的客户再明确要求转人工，走的是**复用**工单
  而不是"等待接入"提示——否则客户会觉得自己的要求被吞了。

### 3.2 旧审批恢复闭环（业务侧）

只"调一次 resume 然后把 content 当成功"会漏掉四种失败，而且**排队中的会话永远走不到
Agent 的 409**——客户不会再发消息，恢复就再也没人做。所以恢复是一个独立闭环：

| 环节 | 实现 | 要点 |
|---|---|---|
| 探测 | `GET /agent/approval/{thread_id}` | 每次恢复前先问；`clear` 直接结案 |
| 恢复 | `POST /agent/resume` | 超时不再盲重试，改为复查后决定 |
| 记账 | `tickets.approval_resume_state` 等 6 列 | `1=待恢复`、`2=已恢复`、`3=重试用尽`；带 `attempts`、`next_at`、`error` |
| 重试 | `recovery.recover_due()` | 常驻在 `chat.worker.run_loop`（默认 15s 一次），与客户消息无关 |
| 幂等 | 工单 + 探测先行 | 重试前先读状态，已 `clear` 不会再 resume；`SKIP LOCKED` + 短租约防多实例重入 |

三条约束：

* **恢复失败不结案**：`_finish_ticket` / `_open_ticket` 仍会给客户工单提示（他确实需要人工），
  但工单上会留下待办，并推一条 `approval_recovery` 给管理员；后台线程继续做。
* **先验租约再动手**：建单与 resume 都在数据库之外，`turns.lease_held()` 挡在第一步；
  失去租约的 Worker 不建单、不 resume、不提交答复。
* **点名转人工也要收口**：`ROUTE_HANDOFF` 不经过 Agent 闸门，但它同样会看一眼旧审批
  （`check_approval=True`），否则旧审批会一直留在检查点里。

老库补列：`recovery.ensure_resume_schema()` 在 maintenance 启动时执行（`information_schema`
判定后 `ALTER TABLE`），`deploy/init/mysql/init.sql` 已同步新列与索引。

## 5. 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `FOUR_AGENT_EVAL` | 未设 | 置 `on` 才允许 `FOUR_AGENT_MODEL_NAME` 生效（评测档） |
| `FOUR_AGENT_MODEL_NAME` | 未设 | 评测档专用模型 id；常规部署忽略 |
| `SUPPORT_V2_THREAD_LOCK` | 未设 | 置 `on` **且**有 `POSTGRES_DSN` 才接跨进程 advisory 锁 |
| `AGENT_RECURSION_LIMIT` | `0` | `0` = LangGraph 缺省 25；`>0` 收紧整图步数 |
| `CHECKPOINT_PING_TTL` | `0` | checkpointer 探活降频窗口（秒） |
| `AGENT_REQUIRE_CHECKPOINTER` | 有 DSN 则 `1` | 置 `1` 且拿不到 saver 时审批判定为 `unknown`（fail-closed）；离线替身置 `0` |
| `CHAT_RESUME_RETRY_SECONDS` | `15` | 业务侧后台重试的间隔；`0` 关闭重试 |
| `CHAT_RESUME_MAX_ATTEMPTS` | `8` | 待办重试用尽后置 `3`（需要人工介入），不再无限重试 |
| `CHAT_RESUME_TIMEOUT` | `30` | 单次 `/agent/resume` 超时（秒） |
| `CHAT_PROBE_TIMEOUT` | `5` | `/agent/approval` 探测超时（秒） |

已退役：`SUPPORT_AGENT_V2`、`FOUR_AGENT_GRAPH`、`X-Agent-Graph`。置任何值都不会改变
执行路径（有测试钉住这一点）；`app/agent/support/rollout.py` 整份删除，
`cutover.enabled()` 仅作为墓碑抛 `RuntimeError`，提示改用 `approval_state()`。

## 6. 回退方法

| 场景 | 做法 |
|---|---|
| 新链路出现异常 | `git revert` 本次收敛提交；契约字段是**附加**的，旧客户端不受影响 |
| 只想关掉调试入口 | 移除 `app/server.py` 里的 `build_support_v2_router()` 一行（生产主入口不依赖它） |
| 换回旧模型 | 不要设 `FOUR_AGENT_EVAL`；或删掉 `FOUR_AGENT_MODEL_NAME` |
| 单进程 → 多副本 | 必须同时设 `SUPPORT_V2_THREAD_LOCK=on` 与 `POSTGRES_DSN`，否则同线程并发仍会丢轮 |
| 用户投诉"答非所问" | 先看 trace 的 `route` 字段：`four_agent`（放行，带 `approval_state`）/ `approval_blocked`（带 `error_code` 与 `status`）；再看 `agents` 列是否委派齐全 |
| 客户侧"一直提示等待人工" | 查 `waiting_ticket(customer)` 是否有未关闭工单；这是业务分流第 4 条，与 Agent 无关 |
