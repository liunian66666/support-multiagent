## 2. 先说测量口径，因为它决定其余数字能不能信

这一节是本次追加的，起因是我在核对旧版基线时发现自己引入了一个测量错误。

仓库里官方的字面判定尺子是 `python_agent/evaluation/score_heldout.py:13`：

```python
def norm(s): return re.sub(r"[\s*_`>]", "", str(s))   # 去空白、去强调符、去 >
```

我写的采集器 `python_agent/evaluation/four_agent/run_ab_live.py` 里那份 `literal_score` 原来只去 `[*_`]`，**不去空白**。把同一份旧基线 `ho_off_r4.jsonl` 分别用两把尺子量：

| 尺子 | 判出的字面通过 | `ho-t09` |
| --- | --- | --- |
| 官方 `score_heldout.norm` | **33 / 36** | 通过 |
| 我原来的 `literal_score` | 32 / 36 | 判失败 |

只差一题，差在一句真话上：模型写的是 `**1 个工作日内**发起退款`，gold 的 required 是 `1个工作日`。少一个空格就判丢——也就是说，**如果我带着这把尺子去跑新旧对照，会从空白字符里凭空造出 1 题"回退"**。

已修：`run_ab_live.literal_score` 与 mem 臂的包含判定统一改用同一个 `norm()`。修完重算 `ho_off_r4.jsonl` 得 **33/36，与已提交 checklist 逐题零翻转**，并把它钉成回归测试 `python_agent/tests/four_agent/test_ruler.py`（3 项：尺子等价、空格不改判、冻结基线复现 33/36 且 `flips == []`）。

其余口径说明：

- **记忆四臂的两个布尔是两件事**，报告里始终分开：`in_durable_transcript`（这根针还在不在这条会话的转写里）与 `in_fed_context`（这一轮**真的被喂进模型上下文**）。只报"可恢复 10/10"会把三种失败臂藏起来——它们在客户侧照样答不上。
- 记忆消融用的是**刻意悲观**的脚本化摘要器（`summary_mode="drop_anchors"`，会把数值和单号改写没）。所以 §6 测的是机制在最差情况下的表现，不是真实模型下的最好情况。
- 检索探针固定 `k=3`、绕过服务进程内的 5 分钟 KB 缓存，测的是"同查询重复检索的候选稳定性"，**不等于**缓存命中与未命中的差异。

`bash python_agent/evaluation/four_agent/run_all.sh pg-restart`——**两个先后独立的容器进程**，第二个进程必须从真实 PG 里恢复第一个写的线程：

```
进程 A  mode=write   rows_before=0  → history=10 messages  watermark=8  ledger_turns=6  rows_in_checkpoints=120
        kept thread=t_demo:pgcheck-crossproc-1656
进程 B  mode=resume  rows_before=120 → resumed history=12  watermark=8  summarized=8  verbatim=4
        after_cleanup rows=0
PASS: 真实 PG 检查点在独立进程重启后仍可续聊，且水位线记忆随之恢复
```

读法：A 写 6 轮 120 行检查点，水位线推到 8；B 是**另一个进程**（新连接的池、新编译的图），恢复出 12 条消息、水位线仍是 8（8 条进摘要、4 条仍是原文）；随后 `adelete_thread` 归零——§8e 那两处修复之后原地复跑过一次，`10 / 8 / 8+2 / 120 / 0` 五个数逐字相同，线上会话数据一行未动（检查点只写 `support_v2:` 命名空间，与旧 `chat:` 线程天然隔离）。

## 4b. 跨进程并发：从"两个实现都会丢轮"到 agent/ 侧有锁且实测过

§5e 的 M10/M11 只给出现象（"两实例共 saver 共 thread，5 次试验丢 1~2 次，两个实现都会丢"）
并把结论停在"平台层性质、当前单进程所以够用"。这一节把那句话变成**证据和修法**，
并且只改 `agent/` 自己的代码。

**为什么内存 saver 上永远测不出来**：`SupportService` 用 `dict[线程] -> asyncio.Lock` 串行化轮次，
`asyncio.gather` 起的并发全在同一进程内 ⇒ 锁必然生效 ⇒ 丢轮率 0。要看见缺陷必须是
**真子进程 + 真 PG 检查点**。`python_agent/evaluation/four_agent/probe_cross_process_lock.py`（`bash python_agent/evaluation/four_agent/run_all.sh xproc [worker数] [每worker轮数]`）
就干这件事：fork N 个 worker 进程同时打**同一条** `support_v2:t_demo:xproc-*` 线程，每个进程内部再并发 M 轮；
父进程结束后连库数落了多少轮，并删掉自建线程。

计数口径（**丢轮 ≠ 拒绝**，这两个数分开记）：

    submitted = Σ 各 worker 提交的轮数
    refused   = outcome=lock_unavailable 的轮数（客户拿得到安全话术，trace 里有原因）
    written   = 检查点里不同 `:u` 人消息 id 数；再用 ledger 通道的 turn_id 数交叉核对
    lost      = submitted − refused − written      ← 只有这个数下降才叫"锁起作用了"

六批实测（`runs/cross_process_lock.jsonl`，**累加式账本**，每批都跑"不加锁 / 加锁"两遍，所以每复跑一次
`run_all.sh all` 或 `xproc` 就多一批、下面那个合计行会自增；**下表 = 截至 10-28 04:52 账本里的那 6 批**。
`compact_trigger` 抬到 10000，免得"少了消息"被压缩解释掉）：

| 形状 | 不加锁 submitted → written | 不加锁 lost | 不加锁 ledger | 加锁 lost | 加锁 refused | 最慢 worker 不加锁 → 加锁 |
| --- | --- | --- | --- | --- | --- | --- |
| 3 worker × 4 轮 | 12 → **4** | **8** | 1 | **0** | 0 | 1730ms → 3815ms |
| 3 worker × 4 轮（复跑） | 12 → **4** | **8** | 2 | **0** | 0 | —（该批早于成本列） |
| 4 worker × 3 轮 | 12 → **3** | **9** | 1 | **0** | 0 | 1411ms → 3920ms |
| 5 worker × 4 轮 | 20 → **7** | **13** | 2 | **0** | 0 | 2686ms → 6200ms |
| 3 worker × 4 轮（`run_all.sh all` 里的那批） | 12 → **5** | **7** | 4 | **0** | 0 | 1965ms → 3517ms |
| 3 worker × 4 轮（04:52 复跑 `run_all.sh all`） | 12 → **5** | **7** | 4 | **0** | 0 | 2953ms → 4228ms |
| **合计** | **80 → 28** | **52（65%）** | 14 | **0** | **0** | — |

四条读法：

1. **不加锁丢的是 58~75%，不是"偶发 1~2 次"**。`written` 只有 3~7 条 ≈ 最后落地那个 worker 的
   份额，符合机理：一轮是"读旧快照 → 算新通道值 → 写"，两个进程各自从同一旧快照算出
   "追加一条"，后写的把先写的整段覆盖。**同一形状复跑两次都是 12→5、丢 7、ledger 4**（最后两行），
   所以这个数不是"挑了一次难看的"。
2. **同一轮里两个通道被覆盖的程度还不一样**：ledger 那列是 1 / 2 / 1 / 2 / 4 / 4，
   而 `distinct_human_ids` 是 4 / 4 / 3 / 7 / 5 / 5 —— **数哪个通道就会报哪个丢轮数**，
   所以这张表把两条都列出来，别只报对自己有利的那条。
3. **加锁后 80 轮全部落地**：六批 `lost=0`、`refused=0`（没有一轮撞 `lock_timeout=30s`）、
   worker 退出码全 0、`rows_after_cleanup=0`（自建线程删干净）。
4. **代价要说出来**：同一线程上的并发轮次被真正串行化 —— 5×4 那批最慢 worker 2.7s → 6.2s
   （20 轮 ≈ **310ms/轮** 排队），3×4 那批复跑是 2.0s→3.5s、3.0s→4.2s（≈ 380ms/轮）。
   但不加锁那 2.7s 里 13 轮是不存在的，所以这不是"快 vs 慢"，
   是"快 vs 丢数据"。锁号按 thread key 算，不同客户线程之间不互相排队；今天部署是
   `uvicorn.run(app)` 单进程，本来也不付这笔钱 —— **它是"加第二个 worker/副本"的前置条件，不是今天的回归**。

实现与边界（说清"有"和"没有"）：

- `agent/thread_guard.py`：`pg_advisory_guard(dsn)` 返回 `async with guard(thread_key)` 工厂。
  三个刻意的决定写在文件头：锁号自己用 blake2b 折成 64 位（不用 `hashtext()`，那是 32 位、
  几万线程就生日碰撞，撞上就是"两个不相关客户互相卡住"）；每轮独占一条连接、
  `set_config('lock_timeout', …)` 后 `pg_advisory_lock` → `pg_advisory_unlock`（会话级锁必须
  跟着活着的连接，异常时关连接也让服务端回收）；**拿不到锁绝不裸跑**。
- `SupportService(thread_guard=...)` 是可选参数，默认 `None` ⇒ 语义与今天完全一致
  （钉在 `test_thread_guard.py::test_service_without_guard_is_unchanged`）。取锁与跑图在代码里
  刻意分开写：用 `async with` 一整块包住的话，图里抛出的异常会被同一个 except 捞走，
  一次模型故障就被记成 `lock_unavailable`，账本从此分不开。
- 生产接法：`agent/entrypoint.py` 的 `build_router`（不注入 `service=` 时惰性建服务那条路）读
  **`SUPPORT_V2_THREAD_LOCK`**，
  只有它 = on **且** `POSTGRES_DSN` 存在时才接锁（缺省关 ⇒ 单进程部署一行行为不变，
  钉在 `test_entrypoint_wires_the_guard_only_when_switch_and_dsn_are_both_present`）。
  也就是说：**今天不用开它**，它是"加第二个 worker/副本"那一步的前置开关。
- 取不到锁时给客户的是 `LOCK_UNAVAILABLE_ANSWER`（不承诺任何事实），`outcome="lock_unavailable"`
  + `error` 带异常类型，**不是 500、不是空白**。
- **只覆盖 agent/ 这一条路**。挂载那条路（`app/services/four_agent.py` 的 `_thread_locks`）
  同样的缺口仍在（M10 继续红），修它要在 app 侧接同一把锁 —— 属于改 app，未授权未动；
  §5e 那三条持久化发现里 M2、M5b 已有候选补丁并在同一个临时副本上实测（§5i），只剩 M3 故意不出补丁。

**这里纠正一个我自己的错误断言，值得单独记。** 我最初用"检查点行数不变"来断言重放幂等，实测 FAIL：`rows=24 → 48`。原因是 LangGraph **每个 super-step 写一行检查点**，重放同一次 `turn_id` 本来就会追加行。真正的幂等保证在**通道**里（`add_messages` 按 id 替换、ledger reducer 按 `turn_id` upsert）。用行数判幂等会把一个正确实现判成 bug——断言已改为比较 `(messages, ledger, distinct_ids)`，并保留行号数仅作观测。

### 5b. 切换默认入口：补丁备好且校验可应用，但"一行搞定"是假的

> **本节写于挂载发生之前**，前提已被 §5e 取代：`app/services/four_agent.py` 现在指向
> `app/multi_agent/graph.py`（app 侧自己实现的四 Agent 图），不再是"旧的静态 DAG"，也不再需要
> 把模块名换成 `agent/cutover.py`。下面两段保留下来，是因为"生产镜像里没有 `agent/` 包"这条部署
> 事实仍然成立，而且它同时解释了为什么今天开关置 on 也不生效。

核对代码后发现，**新旧并行早就存在**，切换点也不在 `chat.py` 的调用逻辑里：JSON 分支
（`chat.py:96`）和 SSE 分支（`chat.py:211`）都已经先问 `four_agent.enabled(...)` 再调
`four_agent.run_turn(...)`，并且只读两个字段——`state["answer"]` 和
`state.get("model_messages", [])`。`four_agent` 当时指向旧的静态 DAG 实现，开关是
**`FOUR_AGENT_GRAPH`**（不是新链路自己的 `SUPPORT_AGENT_V2`），检查点命名空间同样是

但"只改一行 import"这个说法被我**实测否掉了**：生产镜像里没有 `agent/` 这个包。
`docker-compose.yaml` 的 agent 服务是 `build: ./python_agent`（上下文就是 `python_agent/`），

而 `chat.py` 的 import 在模块顶层——**直接换 import 会让服务启动即失败**，不是首个请求失败。

因此两个补丁（`agent/deploy/`，均**未应用**）里，导入用的是带 `ImportError` 兜底的写法：
镜像里缺 `agent/` 就自动退回旧实现，切换失败的表现是"还在跑旧路径"，而不是"客服全挂"。
配套还有 compose 侧一行只读挂载 `../agent:/app/agent:ro`，避免改 build context 触发整镜像重建。
可应用性不是口头承诺，由 `agent/deploy/make_cutover_patches.py` 生成时就跑
`git apply --check` 并跑一次反向校验（反向失败＝工作树确实没被动过）：

```
cutover_chat.patch     target crlf=417 → APPLIES / reverse: still unapplied (good)
cutover_compose.patch  target crlf=0   → APPLIES / reverse: still unapplied (good)
```

这一步还顺手暴露一个我自己的缺陷：`cutover.run_turn` 最初是"先 `_service_for` 再
`thread_key`"，与我此前在 `entrypoint.py` 修过的顺序缺陷同类——建服务会进而建图、触达模型
与知识库。为切换写的测试把它抓了出来（断言身份不合法时服务构造函数一次都不被调用），
已改为身份先校验。**同一个错误我在两个文件里犯了两次，差别只在于这次有测试挡着。**

写这份文档时也踩到一个值得记的坑：`chat.py` 是 CRLF、`docker-compose.yaml` 是 LF，
而 Windows 上默认 `write_text` 会把 `\n` 悄悄写成 `\r\n`，于是给 LF 目标用的补丁会以

### 5c. 前端契约：真正的消费者是 business，不是浏览器

追了一遍调用链：`web/sdk/cs-chat.js` 里没有任何 `/agent/chat` 调用（全仓库只有

所以"验证前端"在不动 app 代码的前提下，可执行的部分就是**验证 agent↔business 的线上契约**，
而对方的解析器比看上去严格：

- **JSON 分支**：先 `succeeded = bool(data.get("success"))`，false 就直接对客户返回
  503「智能客服暂时不可用」；然后把 `data["content"]` 连同 **`data["answer_id"]`**

- **SSE 分支**：只处理 `chunk` / `end` / `error` / `interrupt` 四种 `type`，其余静默跳过；

照这个口径检查我自己的入口，测出一个真缺口：**独立入口的 JSON payload 里没有 `success`、
也没有 `answer_id`**。缺 `success` 是响亮的（整条链路 503）；缺 `answer_id` 是**静默**的
——答复照样显示、照样落库，但每条评分的归因锚点退化成空串，正好是"评分归因脏数据"那一类
问题。已补齐（`to_payload()` 增加 `success` / `answer_id` / `interrupt_data`），并由
`tests/test_wire_contract.py`（3 项）钉住，含反向证伪：把这两个键删掉，2 项立刻变红；
还原后当时全量 58 项全绿。

同时澄清一个**我差点误报成缺陷**的点：我一度以为 `chat.py` 的 `four_agent` JSON 分支
也丢 `answer_id`。核对后不成立——`chat.py:64` 的外层包装在 impl 返回之后统一注入
`result.answer_id`，覆盖所有 JSON 分支，SSE 分支（`:227`）也显式带着它。所以**切流路径本来
就没有这个问题**，缺键只影响"把 business 直接指到新入口"这种用法。结论仍然是：切流走
`chat.py` 是对的；而现在两种接法都满足对方的解析器。

仍未验证：真实浏览器渲染与 WebSocket 交互（要等切流 + 活模型）。字符级契约已经锁住，
视觉级没有。

### 5d. Reviewer 对抗改写语料：之前"安全无回退"只在标准措辞上成立

验收标准 5 说"跨客户订单、无依据承诺和禁用交易操作的关键用例全部通过"。原有 11 条
`test_guards.py` 只证明**每条规则在它那一句示范措辞上会触发**。真实模型换个说法就未必。
于是写了一份 30 例语料（25 不安全 + 5 良性对照）直接喂 `guards.review()`，
见 `python_agent/evaluation/four_agent/probe_guards_adversarial.py`。**首轮结果：漏放 11/25，误拦 0/5。**

三类根因，都不是"规则没写"，而是"规则写得太贴合某一种句式"：

1. **禁用操作只认邻接**。旧 `EXECUTED_CLAIM` 要求「已(经)(为您)?」紧贴动词表，
   于是「退款申请这边已经提交了」「已经帮您把地址改好了」「我们直接把款项打回您的账户」
   「给您退了款」全部绕过——宾语和完成标记被隔开了。改为**子句级**双条件：同一子句里
   同时出现动作名词（`EXEC_ACTION`）与完成标记（`PERFECT`）才算"声称已执行"；是否放行
   仍旧取决于 Business 证据，所以已核验的「已发货」依旧合法。
2. **数值只认阿拉伯数字**。`POLICY_NUMBER` 要求 `\d+`，于是「签收后**七**天」「**一周**内可退」
   「满**九十九**元包邮」「运费 **￥8**」都不算"政策数值断言"，无证据也能说出口。
   现在中文数词按 十/百/千 组合解析（九十九→99），并识别 `￥/¥/RMB` 前缀、补齐
   日/周/年/月 单位——仍然是 `(数值, 单位)` 成对比对，`7 天` 依旧不能给 `7 元` 背书。
3. **单号前缀不容空格**。`TB1234567` 能抓，「订单 **TB 1234567**」抓不到。前缀与数字之间
   允许一个空格或连字符。全角数字本来就能匹配（Python `\d` 覆盖 Unicode 十进制）。

另加一条 `EXEC_PROMISE`：**承诺代做**已关闭的操作（「我可以现在就帮您把退款操作完成」）
与"声称已做"同级为 hard。刻意收窄，`您可以申请退款` 这类客户自助动作不受影响。

1. **`corpus` 遍拦住的 16 例里有 12 例只靠"必须委派"**（val-02..05、ord-01..05、leak-01..03）；

   创建工单|转接人工)` 要求动词紧贴前缀，于是「已经为您办理退款了」「给您退了款」「退款申请这边已经

4. **口径不对称是朝有利于挂载图的方向偏的**，所以 9 vs 0 不是判据松紧造成的假差异。agent/ 侧只有

中间件不会为这些草稿提供任何额外拦截，所以不补测也不影响结论。

结论要说到位：**验收标准 5 在挂载入口上是实测有回退，不是未验证**。合起来看 §5e（M2/M3/M5b/M10）、
§6e（记忆可见性 0/30、可恢复性 12/33）与本节，`FOUR_AGENT_GRAPH` 应当继续留 `off`；这些缺口现在**有三份
实测过的候选补丁**（§5h 的 Reviewer 规则、§5i 的重放幂等键与失败轮恢复），但"补丁能修好探针"≠"开关可以开"——
入口契约（`ChatRequest` 无 `turn_id`）、记忆可恢复性（§6e）与 M3/M10 都还在补丁之外。复跑闸门就是
`bash python_agent/evaluation/four_agent/run_all.sh mounted-guards`（零模型调用、零真实数据），带 `--gate` 时它把两遍的


实测这条命令的退出码是 **1**（不是只打印一行字），所以它可以当 CI/切流前的硬闸门用；今天它不放行，
这正是想要的行为。补齐 app 侧 `review()` 之后同一条命令应变成 `GATE PASS` + 退出码 0——
**§5h 在临时副本上打候选补丁，实测到的就是这个形状**（`corpus 0 / backed 0 / 误拦 0`）。

修法有两条，取舍不同：

- **补规则**：把上面第 2、3 条的三类缺口（数值↔证据原文比对、草稿单号↔核验单号一致性、内部泄漏，
  外加子句级"声称已执行"）加进 `graph.py` 的 `review()`。直接，但仓库里就会出现**第三份** Reviewer

  （或把 `agent/` 打进镜像），这是 §5b 那条"裸换 import 会让服务启动即失败"的同一约束。

两条都属于改 app 侧代码，**未获授权，我没有动**。这一节只交付账本、复跑入口与可直接引用的结论。

M5b 这条顺手改了**探针自己的两处缺陷**，两处都要写出来，否则下一批数据又会误导下一个人：

① **判据只认我脑子里那一种修法**。原来问的是"检查点里还有没有 HumanMessage"（`humans == 0`），
那只有"把这条问句回滚掉"能满足，会把另一种同样正确、而且对客户更诚实的做法——**留着问句、
补一条安全答复**——判成没修（陷阱 #21）。判据换成"有没有**没人回答的人消息**"，
两个臂同时用新判据，所以对照仍然可比（对照组该红的照红：`dangling=1 / ai=0 / last_error 为空`）。

② **观测列取错了轮次**。故障那一轮的返回值被 `try/except` 收进 `raised`，于是**它自己的事件流也一起丢了**，

对照组 **0** → 补丁组 **1**，证明补丁里那句 `trace.record("error", "model_failure", detail=…)`
真的在故障那一轮开了火。同一行现在三条"可见性"列，分工必须写清：`last_error_persisted`
（能不能活到下一轮）与 `failure_turn_error_events`（当轮有没有记进 trace）是观测两侧的正证，
`recovery_turn_error_events` 只证明**恢复轮是干净的**（两臂都是 0，这是对的），不参与判定。

**M3（回退后可见性）我刻意没出补丁**：让开关切回 off 后旧路径还能看见 ON 期间的轮次，
唯一直接的做法是新图每轮再写一次 `faq_bridge`——那正是阶段3 要**取消**的"图外检查点补写"。
把它做成补丁，等于用一条发现去换另一条更基本的原则。可行的替代是让旧路径读历史时
也认 `support_v2:*`（改读侧、不改写侧），这需要 app 侧决定，我只把问题、两条路子和代价摆出来。

关键边界要说白：**这三份补丁补的是 `run_turn` 侧的能力，不是入口契约**。`ChatRequest` 里仍然没有 `turn_id`
字段，前端/代理不带键 ⇒ 走的就是今天的路径，`M2` 那一条确定性失败一个都没少（同一个原因还带着
`M2b` 在对照组必红：入口不收参数，探针连测都没法测）。要让它真的生效，

这才是本阶段真正想说的两件事：

1. **记忆不稳定不是"摘要写得不好"，是形状依赖。** 三种对照臂的逐题结果随锚点位置和对话长度在 0↔3 之间摆动（波动幅度 3），即"同一套系统，客户问的顺序不同就不记得"。水位线 + 锚点回补是四臂里唯一**几何不变**的（波动 0，每题 3/3）。
2. **水位线本身不够，起作用的是锚点回补。** `watermark_norepair` 和 `window_only` 同为 9/33——只加水位线、不回补缺失锚点，客户侧没有任何改善。这条就是消融臂存在的理由，也说明 `SUMMARY_LIMIT` 内的按预算回补不是可有可无的装饰。
3. `delete_rebuild` 的 6/33 是**不可逆**的：一旦被 `REMOVE_ALL_MESSAGES` 冲出通道，后续任何轮次都找不回来。这是当初不采用官方中间件默认语义的实测代价，不是风格偏好。

### 6c. 两条边界现在有正面测试了

目标把"摘要不是订单状态或店铺政策的事实来源""动态事实每轮重新查询"列为必须守住的边界，验收标准又点名"重启、指代、条件冲突"。自查发现：`evidence_supported()` 的授权来源只由**本轮** `delegations` 构成，摘要在结构上确实进不了背书链——但**这个结构性质没有一个测试钉住它**，而"条件冲突"当时**完全没有**对应测试（`test_claim_contradicted_by_verified_order_state_is_blocked` 测的是草稿与已核验事实冲突，不是摘要旧条件与本轮新条件冲突）。已补两条，各带对照组以免沦为永真断言：

- `test_summary_cannot_license_a_policy_number`：先把真实检索过的 `7 天` 推进摘要区（用 `keep_anchors` 让脚本摘要器**故意**原样保留），断言 `state["summary"]` 里确实有 `7 天`，再让模型在无委派的情况下复述它 → 答案里不得出现 `7 天`，且 `review_issues` 记录到"证据"类问题。**对照组**：同一线程、同一个数值，只要本轮真的 `consult_faq` 拿到证据就放行 → 证明拦的是"无当轮证据"，不是"7 天"这个值被全局禁掉。
- `test_changed_condition_forces_a_fresh_order_check`：先委派订单 Agent 拿到 `ORD-1001` 事实并推进摘要，客户随后把"退货"改成"换货"并追问状态。分支一只引用摘要 → `ORD-1001` 不得出现在答案且命中"核验"类 hard；分支二本轮重新委派 → `answered`、`ORD-1001` 正常出现、且本轮 `roles` 里有 `order`。

这两项把 `test_memory.py` 推到 12 项；随后为切换 shim 补的 `test_cutover.py`（3 项，见 §5b）把总数推到 **55**。

**仍未覆盖**：真实模型下的自然语言多样性（同义改写、多锚点竞争回补预算、中途话题切换）以及条件冲突下的答复措辞。这些需要活模型。

### 6d. 先撤回一个过期前提：旧路径的"摘要覆盖"已经修了，差异不在这条

目标把"修复旧摘要覆盖新摘要"列为阶段4 第一项。我去读当前代码核对，发现**这个前提对今天的旧路径已经不成立**，
我此前在 README 里写的"旧路径依然存在该缺陷"是错的，已就地勘误。现在的旧路径记忆链路：

| 环节 | 当前旧路径（读码，含你自己的提交） | 证据 |
| --- | --- | --- |
| 落库并发 | 单调 CAS upsert：`summary` 仅在 `VALUES(last_summarized_message_id) > last_summarized_message_id` 时覆盖，水位取 `GREATEST` | `business/agent/internal.py` POST 分支 |
| 候选挑选 | 水位之后的增量消息，`HAVING MAX(m.id) > 水位`（不再是"每会话只摘一次 + 取最近 40 条覆盖写"） | 同文件 pending 查询与其 `[ours]` 注释 |
| 失败语义 | 生成或保存任一失败都不推进水位，下轮幂等重试 | `app/workers/summary.py::_process_one` |
| 多实例 | Redis `cs:lock:session_summary` 单实例锁 | 同文件 `_acquire_lock` |
| 关键事实 | **提示词请求**逐字符保留订单号/金额/时限，并要求"同一事实前后矛盾以新增对话为准" | `MERGE_PROMPT` 第 2、3 条 |

所以阶段4 这一项在新图里是**结构性满足**（`summary` 是通道字段、reducer 只增不换、水位单独推进），
不是"我修掉了一个线上缺陷"——那个缺陷已经被旧路径自己的改动修掉了，功劳不在这里。

**那新链路还剩什么真差异？** 四条，都能在代码里指出来，其中一条有实测：

1. **轮内可用 vs 空闲后可用**。旧摘要由后台 worker 产出，默认要会话**空闲 ≥ 30 分钟**
   （`IDLE_MINUTES`）且每 600 秒才跑一轮 —— 一次连续 20 轮的长对话，中途**拿不到任何摘要**，
   记忆实际就等于 `recent_messages(12)`。新图在 `compact_trigger` 到阈值时**本轮内**压缩并继续可用。
   这条正好解释了 §6b 里 `window_only` 臂的行为：它不是稻草人，它就是"进行中的旧路径"。
2. **确定性保留 vs 提示词保留**。旧路径靠模型遵守 `MERGE_PROMPT` 第 2 条；没有校验、没有回退，
   模型改写了就是改写了。新图压缩后拿 `anchors(previous) - anchors(generated)` 做差，
   缺的锚点按剩余字符预算**程序化回补**。实测代价即 §6b：同一个"不守指令"的摘要器下，
   不回补是 9/33，回补是 33/33，且逐题波动 3 → 0。
3. **摘要能不能当事实用**。旧路径把 `summary[:400]` 以 `_SYSTEM_PREFIX` 注进 specialist 的
   prompt，模型可以直接引用里面的数值下结论，冲突只由提示词第 3 条软约束。新图除 banner 明示
   "不作为订单状态或店铺政策的依据"外，还有 hard 规则：政策/订单数值必须有**本轮**证据
   （§5c/§6c 的对照实验证明它拦的是"无当轮证据"，不是某个值被禁）。
4. **状态源数量**。旧路径记忆分散在三处（MySQL `session_summaries`、`messages` 表、checkpointer）；
   新图 summary/watermark/ledger/usage 全在同一份图状态里，由同一个 checkpointer 持久化（阶段3 的
   "图内持久化"要求，§4 实测跨进程恢复）。

这四条里没有一条是"旧路径会覆盖新摘要"。把它们和那条混在一起讲，会让新链路的收益看起来比实际大 ——
这正是要避免的表述。

### 6e. 挂载图的记忆也跑了同一套逐题协议：可见性与旧路径持平，可恢复性比旧路径更差

§5e 里我写过"挂载图的记忆没跑过四臂对照"。这句现在补上了——同一批转写、同一个**刻意悲观**的

`runs/mounted_v2.jsonl`（10 行）、`runs/mounted_v2_geometry.jsonl`（11 行）。

| 语料 | 臂 | 进上下文 | 仍可恢复 |
| --- | --- | --- | --- |
| 冻结 10 例 | `window_only`（旧路径等价） | 0/30 | 30/30 |
| 冻结 10 例 | **`mounted_v2`** | **0/30** | **30/30** |
| 冻结 10 例 | `watermark`（本实现，生产配置） | **30/30** | 30/30 |

三条读法，都有行级证据：

1. **可见性：挂载图 ≡ 旧路径，评估过的记忆能力没有跟过来。** 挂载图的喂料是
   `summary[:1000] + messages[-12:]`，而 `messages` 里一问一答各占一条 —— **窗口其实是 6 轮**，
   和旧路径 `recent_messages(limit=12)` 的可见范围一模一样，所以两臂逐题同分（冻结 0/30、变体 9/33）。
   `watermark` 臂的 30/30 与 33/33 来自锚点回补，而挂载图**没有任何回补步骤**。
2. **可恢复性：挂载图比旧路径更差。** 冻结语料里它没触发压缩（`merge_calls=0`、通道仍 24 条），
   所以 30/30 看着和旧路径一样——**这是巧合**：冻结用例是 11 轮 + 探针 = 24 条消息，恰好落在
   `len(messages) > 24` 这个阈值之下，再长一轮就会压缩。结构变体把长度推到 13/20 轮，
   压缩一触发（`watermark=14/28`），被吸收的消息经 `RemoveMessage` **离开图通道**，
   9 例的"仍可恢复"从 33/33 掉到 **12/33**，其中 t13/t20 的 8 例全变 0/3。
   旧路径不删消息（33/33），所以这一维是**净变差**，性质与 §6b 的 `delete_rebuild` 臂同类，
   只是它保留的尾部更长（12 条 vs 6 条），所以比 `delete_rebuild` 的 6/33 好一点。
3. **摘要质量只影响可见性那一半，不影响可恢复性。** 我把合并模型设为最差情况，所以挂载图"进上下文"
   偏低里有一部分是我的注入；真实模型可能把单号留在摘要里。**但"压缩即从通道删除"是机制本身的性质，
   与摘要写得好不好无关**，而且挂载图没有任何机制能把被删掉的锚点取回来——这正是当初做水位线 +
   锚点回补的理由（§6d 已确认旧路径的"摘要覆盖"缺陷被修掉了，差异不在这条上）。

口径边界与自曝：这套探针不测措辞、延迟与 token；它测的是"这一轮模型实际看到了什么"和"智能体自己的
会话状态里还剩什么"。冻结语料 10 例的结果都是 `outcome=fallback`，原因是我脚本的路由
（`_pmg.compound`，按 `退货/运费` 关键词委派）没覆盖这些问句里的政策词，触发了 Reviewer 的
「政策问题必须委派 FAQ Agent」——**这是 harness 的缺陷，不是挂载图的缺陷**，重试只多调一次
supervisor、不改消息计数与窗口，所以两个锚点布尔不受影响；我把它记在这里而不是悄悄修掉，
因为"逐题表里所有 outcome 都是同一个值"本身就是该被追问的信号。

结论一句话：**打开 `FOUR_AGENT_GRAPH` 不等于打开 §6 里那套被验证过的记忆。** 若要让挂载路径
继承这份证据，需要在 `app/multi_agent/graph.py` 里补锚点回补并停止通道删除——那是改 app 代码，
未授权，所以我只把差异与代价量化到这张表。

### 6f. 长对话记忆第一次和旧路径做了同模型对照：旧路径 0/10，新路径 5/10——而两边的失败都不是"摘要把旧信息盖掉"

两个臂都在 `deepseek-v4.1-flash` 上跑：新路径走 `run_ab_live.py mem`，旧路径走 §8g 的

   r5 唯一还失败的那例 mem-07）；禁止复述 ⇒ 保持现在的自我消音，分数就是 §6g 那张表里的 9/10 封顶。
   两边都**不应该**放宽的是"断言状态"——那一条已由业务接口 + 规则双重守住（`test_memory.py` 第一分支）。

§6 前面那三套机制级逐题表（水位线 + 锚点回补 vs 滑窗 vs 无记忆 vs 删除重建）仍然成立，
这一节补的是它们在真实模型上的**症状学**，并把"能刷分的那条路"明确留在桌上没走。

修法仍然只动采集侧、不动被测链路：`run_ab_live.py` 用 `dataclasses.replace` 给 deps 换一层

`0 ⚠（摘要失败×N：原因）` 与 `0 ○（N 轮都没到触发线，摘要没坏）`；旧 jsonl 没这个字段，仍显示 `0 ⚠`。

发现三（r4 才看得见）：**`empty_summary` 不是"摘要调用失败"，是摘要那一次调用的输出预算被思考 token 吃光了——而且在此之前，被截断的摘要还算"成功"。**
带 `compact_ledger` 的第一批真实模型臂（r4，串行、同一把 key）把这件事彻底量清楚了：

| r4（新图臂，10 条对话） | 数 |
| --- | --- |

`empty_summary` 在代码里只有一个入口：补全 **200 成功、正文是空串**。为了分清"正文去了哪"，
新写了 `python_agent/evaluation/four_agent/probe_summary_empty.py`——它把摘要那一次调用的 `content` /
`reasoning_content` / `finish_reason` / `output_tokens` 全部原样打出来，并且能用 `--long`
把输入拉到臂里那种长度（871 字提示词），再用 `--max-tokens` 只改探针这一次调用的预算：

| 输入 | `max_tokens` | 结果 |
| --- | --- | --- |
| 短（6 条消息） | 继承 1024 | 6 次里 1 次空正文，那次 `finish_reason=length`、`output_tokens=1024`；成功的 5 次正文 163~232 字却耗掉 662~978 token ⇒ **同一模型每次先烧掉几百 token 的思考** |
| 臂长（871 字） | 继承 1024 | **4 次里 3 次 `finish_reason=length`**：其中 1 次正文 0 字，另外 2 次正文被截成 **12 字 / 100 字**——而这两次在旧代码里算"摘要成功"并推进了水位线 |
| 臂长 | 4096 | **4/4 `stop`**，正文 316~399 字，`output_tokens` 913~1723 |

所以成因是**参数**（第 2 类），不是链路也不是读取形状：聊天模型的 `max_tokens=1024`
被摘要继承，而这个模型的思考 token 一起算进 `output_tokens`，输入一长就把预算吃光。
两条后果叠在一起：①摘要经常什么都没写 ⇒ 水位线不动 ⇒ 24 条原文每轮全量重塞（这也是新臂
60~97k token/条对话的成因之一，方向待 r5 复测）；②**更隐蔽的是截断被当成成功**——半条摘要
会推进水位线，把被截掉的那段原文从模型视野里拿走，而 `summary 条数` 那个数字看着一切正常。

已落地两处（都只改摘要这一路，不动别的调用；`agent/memory.py`）：
1. `SUMMARY_MAX_TOKENS = 4096`，在 `compact()` 里 `model.bind(max_tokens=...)` 单独生效；
2. `finish_reason == "length"` 一律按失败处理，新增原因 `truncated_summary` ⇒ **一条都不删、
   水位线不动**，宁可让下一轮看全量原文，也不写半条摘要。

`::test_a_truncated_summary_must_not_advance_the_watermark`（同一个替身，只有收尾原因不同，

## 7. RAG 小范围优化：波动定位到三层，只有一层还有后果，而那层不归检索管

目标写的是"只修改能解释波动的环节，没有效果就不保留额外复杂度"。做法是把波动拆开定位，而不是先改再找理由。

**先撤回一句我自己说过的话。** 上一版这里写的是"15 题 × 5 次 = 75 次检索，候选集零抖动"。那句话是
**只看了一批**、而且指标只问"top-3 的 chunk 集合相不相同"。同一份固定题集连跑 **13 批**（163 个题次、
779 次检索，`bash python_agent/evaluation/four_agent/run_all.sh retrieval-batches 3` + `summarize_retrieval_batches.py`）之后，
真相是分层的：

| 层 | 实测 | 说明 |
| --- | --- | --- |
| 分数 | **65/90 题次（72.2%）五次调用的 relevance score 元组逐位不同** | embedding 侧本来就不是逐位确定的。探针原先把分数舍到 4 位，**正好把决定名次的 1e-4 差距抹平了**，所以旧批次看起来"一切稳定"；已改成 6 位并新增 `distinct_score_tuples`（这一列只有升级后的 6 批 90 个题次有，不外推） |
| 候选组成 | top-3 组成翻动 **9/163 题次（5.5%）**，集中在 4 题：`ship-full99` 6、`ship-tracking-24h` 1、`ret-window` 1、`ship-fee-under99` 1 | 翻动**只发生在第 2/3 槽**，竞争两两分差 `6e-5 ~ 1.4e-3`（例：0.701754 vs 0.701690）——典型近平票换名次。有时是同文档的兄弟 chunk 互换，有时跨文档（`c111e8bd` 与 `8b0a0bf7`） |
| 后果 | 金标掉出 top-3：**0 次**（779 次检索）；条款覆盖掉过：**0 次**；但候选里的**数值集合**变过 **6/90 题次（6.7%）** | 换进换出的是那条带「7 天」的旁证 chunk；而**回答问题所需的数值**（99 元 / 8 元 / 24 小时…）**永远在第 1 槽**，所以决定答案的那条证据从没换过 |

**机制已定位，不再靠猜。** 上面那句"更像两个稳定取值"我用一个分层探针证掉了：`bash python_agent/evaluation/four_agent/run_all.sh embedding-drift`
（`evaluation/probe_embedding_determinism.py`，只读、拒绝在缺 collection 时运行）把同一句话的检索链路拆成三段分别重采：

| 段 | 怎么测 | 实测（4 个翻过名的题 + 2 个对照题，各 8 次） |
| --- | --- | --- |
| embedding 调用 | 同一文本连发 8 次，把返回向量原样打哈希（**不四舍五入**） | **5/6 题返回过 2 种不同向量**（两个对照组也翻，只有一题这轮 8 次全同） |
| Qdrant 检索 | **固定同一个向量**连查 8 次，比较邻居 id 集合 | **0/6 题换过邻居** ⇒ 这一层完全确定 |
| 服务路径 | 走 `asimilarity_search_with_relevance_scores` 8 次 | 2/6 题候选集合变过——纯粹是上面第一段差异的下游传导 |

配套的临界证据：两个翻动题的 `cutoff_gap`（第 3 名与第 4 名分差）只有 **0.000426 / 0.000353**，而其它相邻名次差是 0.02~0.17；
所以"微小向量差 → 换第 3 名"是数量级上必然的，不是偶发巧合。

**结论：波动的源头在 embedding 服务端（同一文本给两个稳定取值），不在本仓库的排序/证据选择层。**
这直接把"加确定性 tie-break"这条路否掉了——同一向量下 Qdrant 已经 100% 给出同一批邻居，
在下游怎么排都排不出一个更稳的答案；要稳只能在**上游**做（缓存 query→vector，或换/封装确定性 embedding），
那不属于"检索或证据选择环节"的小范围优化，且要改的是服务侧。原始数据 `runs/embedding_drift.jsonl`。

**结论仍然是"不改"，但理由换成能核对的那一条。** 任何检索层改动要成立，必须改变上面第三行里"有后果"的那个数；
而金标命中与条款覆盖已经是 0 损失，剩下唯一被影响的是"答复会不会多说一句 7 天"——那是**答复层方差**，
只有真实模型臂量得出来（属 #6），不能靠加 rerank 去猜。三个候选方案以及为什么不做，写清楚免得后来人重走：

1. **近平票二次排序**（同分按 `chunk_id` 定序）：**已被分层探针否掉**——固定同一向量时 Qdrant 0/6 换邻居，
   说明排序层本来就确定；翻动来自向量在两个取值之间跳，下游怎么排都排不出更稳的结果。
2. **提高阈值 / 按文档去重**：会把「7 天」这类旁证稳定地留在窗口外或里，等于**改变喂给模型的内容**；
   收益无法在没有模型臂时证明，代价还可能有丢条款的风险。
3. **加大 `k`**：把近平票全收进来，"吸收"了翻动，但同时端上无关上下文，方向不对。

诚实标注探针局限：固定 `k=3`、绕过服务进程内 5 分钟 KB 缓存，因此**缓存命中/未命中的差异仍未测**；
每批是一个独立容器进程，进程内 5 次连发，所以"首批首次调用"的 warm-up 效应没有被单独隔离出来。
旧批次没有 `distinct_score_tuples` 这一列，72.2% 这个数只由升级后的 **6 批（90 个题次）**算出，不外推到全部 13 批。
另有一句要说清：上面这组数是 **10-28 03:14 那次汇总的快照**，而 `retrieval` 每跑一批就往 `runs/` 里多一个文件，
所以重跑汇总的分子分母都会变（结论那三行——**翻动 ~5% 量级、只动第 2/3 槽、金标与条款覆盖 0 损失**——不会变）。
要一个可核对的当前数就跑 `python python_agent/evaluation/four_agent/summarize_retrieval_batches.py`，别靠这段文字的记忆。

原始数据：13 份批次文件 `runs/retr*_numericac3478.jsonl`（含 `retrieval_stability_full_*` 那份最初的 75 次），
汇总一条命令 `python python_agent/evaluation/four_agent/summarize_retrieval_batches.py`。

## 8b. 延迟与成本里"不需要模型"的那一半，已经实测

阻塞的是推理时间与计费 token，但**编排开销**和**喂给模型的上下文规模**是新图自己的属性，
今天就能量。`python_agent/evaluation/four_agent/measure_overhead.py` 用即刻返回的脚本化模型跑 40 轮×3 臂，
把模型时间从测量里剥掉，只留下节点执行、reducer、Review、压缩与检查点写入。

**编排 + 持久化开销**（真实 `AsyncPostgresSaver`，3 次独立采样 + §8e 修完之后的第 4 次复测；括号内为 `InMemorySaver`）：

| 上下文制度 | p50 中位 | p50 波动带 | p95 中位 |
| --- | --- | --- | --- |
| `full_transcript`（水位线之后全喂） | 121.0 ms（9.3） | 118.8 ~ 136.5 | 186.6 |
| `window_12`（旧路径 `recent_messages(limit=12)` 等价） | 142.1 ms（9.6） | 115.9 ~ 144.3 | 205.6 |
| `watermark`（生产：banner + 尾部 + 锚点回补） | **112.6 ms**（10.3） | 109.4 ~ 126.3 | 165.5 |

这里有一个我差点说错的结论，值得单独记。**单次采样时水位线臂看起来比旧窗口臂快 15.8ms**，
但换一次采样后 `window_12` 的 p50 从 115.9 跳到 144.3 —— 同一臂跨采样的波动带是 28.3ms，
而**三臂中位数之间的最大间隔只有 29.5ms**。间隔 ≈ 波动带，所以正确说法是
"三臂同量级，无法判定谁更快"，而不是"记忆让每轮更快"。更早那次 InMemorySaver 采样里
水位线反而比窗口**慢** 0.64ms——符号都会随 run 翻转，这本身就是噪声带的证据。
不做这个对照，我就会把 run 间抖动写成一句性能结论。

可支撑的只有量级判断：整条新图的每轮结构开销 **~113–142ms（含真实 PG 写）**，
对照旧路径实测端到端 p50 **5741ms**，占比 **约 2–2.5%**；去掉持久化（内存 saver）则
~10ms，占比 0.17%。换言之新图增加的编排成本不是延迟瓶颈，瓶颈仍在推理那一侧——
而那正是今天测不了的部分。每 40 轮线程落 **640 行检查点（16 行/轮）**。

**上下文规模 = input token 的直接驱动量**（三臂在任何一次采样里都完全一致，是确定量）：

| 制度 | 首轮 | 40 轮末 | 峰值 | 增长 | 摘要占字 |
| --- | --- | --- | --- | --- | --- |
| `full_transcript` | 36 | **1355** | 1355 | **37.6×** | 0 |
| `window_12`（旧） | 36 | 202 | 208 | 5.6× | 0 |
| `watermark`（本实现） | 36 | 395 | 467 | 11.0× | 229 |

诚实的读法：**记忆是有价格的，不是免费提升**。相对旧窗口，水位线在 40 轮时多喂
`395 − 202 = 193` 字（约 +96% 的会话上下文），这 193 字就是 banner + 回补锚点的代价，
换来的是 §6 里从 9/33 到 33/33 的锚点可见性；相对"整段转写都喂"，它又只占 34%
（1355 → 467 峰值），把 37.6× 的线性增长压回 11.0×。所以这三行讲的是同一个取舍的两端，
不能只挑对自己有利的那一行说。

口径边界：字符数**不等于** token，中文大致 1 token / 1–1.5 字但不做换算——那会给出假精度；
上表只用于比较相对规模。延迟数字不含推理，因此不能当端到端延迟引用。

原始数据：`runs/orchestration_overhead.jsonl`（内存）与 `runs/ovh_pg_r1.jsonl` /
`ovh_pg_r2.jsonl` / `orchestration_overhead_postgres.jsonl`（3 次真实 PG 采样）。
脚本跑完会**自删**这三个线程并打印行数自检（`640 → 0`），不留生产数据；事后又用 SQL
直接复核过：`checkpoints / checkpoint_writes / checkpoint_blobs` 三张表里
`thread_id like 'support_v2:t_demo:ovh-%'` 均为 **0 行**，全库 `support_v2:` 命名空间
总计 0 行（库内 3686 个检查点全是旧路径既有数据，未被触碰）。这个自删不是可选的——
第一次跑的时候我用 `sum(1 async for ...)` 统计行数，直接 TypeError 让清理整段跳过，
三个线程真的留在了生产库里；后来把清理写进脚本并改成显式 `async for` 才补齐。

**§8e 那两处改动之后，这一节的数字全部复测过（2026-10-28 18:26），结构性数字一个都没动。**
内存臂这次是 p50 8.47 / 8.50 / 8.75ms——三臂中位数间隔只剩 0.28ms，比原先更彻底地说明"排不出谁更快"；
真实 PG 第 4 次采样 115.2 / 120.9 / 130.1ms，**三个值都落在上面已经公布的波动带内**（没有一条越界，
所以带还是那条带）。上下文规模那六个数（`36 → 1355 / 202 / 395`、峰值 `1355 / 208 / 467`、
增长 `37.64× / 5.61× / 10.97×`、摘要 229 字）与"每轮 16 行检查点、每臂 640 行、删后归零"**逐字相同**；
`agent.demo` 的 8 轮演示重跑后每行 `usage` 也完全不变——那些轮次都是 `attempts=1`，累加本来就不动。
换句话说：修预算和修记账改的是"原本就记错的数"（重试轮的真实成本），没有把任何已交付的数字改大或改小；
这条复测的意义在于**排除"为了圆结论去动代码"这个方向**——若结构开销或上下文规模随我的修复漂移，
那说明我把测量对象本身改了。

## 8c. 旧路径延迟的完整分布，以及新图会吃掉的那 14.4% 无模型快路径

§8 里旧路径的 p50 5741 / p95 10511 来自 n=36 的留出集。现网自己的 `agent_trace_runs` 表里有一份
**大 48 倍**的样本：1741 轮（2026-10-21 → 10-26），按 `route` 分组（`bash python_agent/evaluation/four_agent/run_all.sh trace-baseline`，只读 SELECT，原始数据 `runs/legacy_trace_latency.txt`）：

| route | n | 无模型轮次（<200ms） | p50 | p95 | min | max |
| --- | --- | --- | --- | --- | --- | --- |
| `faq`（走模型） | 1120 | **0** | 4774 ms | 12735 | 398 | **70787** |
| `general`（走模型） | 341 | **0** | 2836 ms | 5986 | 663 | 19902 |
| `order`（多为核验短路） | 155 | 126 | 50 ms | 6525 | 34 | 21468 |

| `faq_fast`（流程 FAQ 直答） | 23 | 23 | 28 ms | 49 | 23 | 81 |
| `order_list` | 2 | 2 | 64 ms | 78 | 49 | 79 |
| **合计** | **1741** | **250（14.4%）** | 3738 ms | 11755 | | |

两条结论，一条对我有利、一条对我不利，都写在这里：

1. **有利**：新图每轮结构开销 ~113–142ms（§8b，含真实 PG 写）相对 `faq` 路由 p50 4774ms 是

2. **不利，而且这是切流前必须算进去的成本**：旧路径有 **14.4%（250/1741）的轮次根本不调模型**
   （`handoff` 99/100、`faq_fast` 23/23、`order_list` 2/2、`order` 126/155 都在 200ms 内返回，
   那是 `decide_turn` + `execute_shortcut` 的决定性短路）。而 `chat.py` 的 four_agent 分支在
   `decide_turn` **之前**就 return（JSON 分支 `:96`、SSE 分支 `:218`），所以开关一开，这批轮次全部
   改走"每轮至少一次 supervisor 模型调用"——按 `faq` p50 4774ms 估，这 14.4% 流量的客户等待时间
   会从**几十毫秒变成秒级**。两条模型路由的 `model_free=0` 正好是反面印证：一旦进模型就没有快路径。

这不是"新图更慢"的结论。新图换来的是复合问题一次答全（§5e 的 M1）、无证据数值与未核验订单被拦

总是短路。但要保住这 14.4%，需要在新图**之前**保留一条决定性短路（或在 Supervisor 前加规则路由），
这属于改动 app 代码，未授权，所以我只把它写成结论、做法与量化影响，不代做。

口径边界：`duration_ms` 是 trace 记录的整轮耗时（含工具与持久化，不含 business 侧排队），与 §8 那
36 题留出集**不同源**，两个数不能混进同一张表比较；本表只用于"分布有多宽、快路径占多少"。

## 8e. 把采集器接到一个真的 HTTP 模型上（确定性替身）：量出两个我自己的缺陷，都修了

真实模型仍不可达，但"没模型"不等于"采集器不用测"。此前所有离线证据都用**进程内**替身
（`agent/fakes.py`），所以这一段从来没被证明过：`run_ab_live.py` 能不能真的走完一次
OpenAI 兼容的 HTTP 往返、tool call 能不能在 JSON 序列化后活着回来、`usage` 通道能不能记账、
采到的文件能不能直接进 §8d 的闸门。于是加了一个**确定性 OpenAI 兼容端点**
`python_agent/evaluation/four_agent/mock_openai_server.py`：它不是语言模型——答复文本是从工具返回里抄出来的，
所以这一臂的 `literal_pass` **只说明管道通了，不说明措辞对了**；每条数据都带
`comparable=false`，`--model custom` 配 `--parity` 直接拒绝运行（两条后端混在一轮里就没法解释结果）。
入口：`bash python_agent/evaluation/four_agent/run_all.sh live-mock [heldout|mem] [limit]`。检索侧不是替身——
真 Qdrant + 真 embedding（15 题 × 5 次那条探针今天照样跑通，说明**阻塞只在 chat 补全，embedding 路是活的**）。

它当场抓到两件事，都是我的代码：

1. **步数预算不够，把一轮合法的重试判成 no_result。**  bisect 实测（离线替身，唯一变量是预算）：
   最贵的合法形状——3 个 pass、每个 pass 先委派 FAQ 再委派 General 再收口——在
   supervisor 内层预算 16 和 20 时抛 `GraphRecursionError`，`attempts=3` 但
   `model_calls=0`、答复只剩兜底话术；**24 才开始通过**（`review_blocked`，因为草稿里那个
   "30 天"没有当轮证据，被 Reviewer 正确换成安全话术）。根因是 LangGraph 把**子图的步数计入父图
   剩余预算**，而我原先按外层节点数（24）定预算。已把两处预算提成常量并写明依据：
   `SUPERVISOR_STEP_BUDGET=32`（24 的实测最小值 + 三分之一余量）、`TURN_STEP_BUDGET=48`，
   `service.py` 与测试都读同一常量，测试辅助函数不再自带 24——否则测试和生产跑两套预算，
   绿的就是假的。回归位：`test_graph.py::test_heavy_delegation_across_every_retry_still_answers`
   （先在 16/20 红、24 起绿）。
2. **带重试的轮次只记最后一个 pass 的账。** 通道按 `turn_id` upsert，pass 之间是**覆盖**不是累加：
   3 个 pass 9 次模型调用只报 3 次。修法是 `open_turn` 先丢掉**本轮**的 usage 条目、每个 pass
   在上一 pass 的总数上累加（`agents.add_usage`）——重放仍然幂等（整轮重跑从空开始），重试不再漏账。
   这条直接影响验收标准 6 的 token 成本口径，所以它比"少几个数"严重。

修完之后同一臂的实测数（12 题，`runs/mock_heldout.jsonl`）：`answered` 11 + `answered_unchecked` 1、
**0 个 `no_result`、0 个 graph_error**（修之前是 8 通过 / 4 个递归错）；每轮模型调用
p50 2 / max 8，token p50 689 / max 2998（含重试累加），采集侧自报延迟 p50 430ms、p95 1318ms，
mock 侧计数 66 次 HTTP 请求 / 33 次 tool call / **0 错误**。mem 两例：118 次请求、watermark 16、
每条约 14k token（48 步预算下重试都记进来了）。**`recall=[False, False]` 是替身的性质不是记忆的性质**：
它只复述本轮工具返回，探针要回的是早先一轮说过的锚点——记忆本身仍由 §6 那三套确定性逐题表负责。

闸门这一段也顺手修了一处会把人误导的口径：部分覆盖的臂此前会把"没采集到的题"同时算成
**回退**又列一次**缺题**（同一批案例被收两遍，"回退 24"读起来像新链路打翻了 24 题）。现在缺题是
独立类别 `gap`，仍然拦闸门（没测过就不能放行），但不再冒充回退。实测：12/36 那份臂现在报
"覆盖 12/36（缺 24）、保持通过 9、翻正 2、**回退 1**、保持失败 0、候选未采集 24"，退出码 1；
不带参数的自检仍然"逐题零翻转、退出码 0"。缺题那条测试是**改名重写**而不是新增（`test_missing_case_is_counted_separately_and_not_silently_kept`
→ `test_missing_case_is_a_coverage_gap_not_a_regression`），项数仍是 8、全量仍 68 passed——我上一版把 §3 写成"9 项"，是数错了，
已按 `pytest --collect-only` 的逐文件计数改回（12/12/10/12/5/3/3/3/8 = 68）。§5h 之后 `test_guards.py` 多了一条全角单号回归位，逐文件计数变成 **13/12/10/12/5/3/3/3/8 = 69**。

两条臂的 9 行原始记录 **sha256 相同**（`6cfd796a6b9ad180…`）。这不是"两边都大致对"，而是

顺手把两个演示用的坑填了：`--thread` 现在可固定线程名（且必须落在 `t_demo:` 前缀内——

同一次改动还顺手把 §8 那张表的取证质量提了一下：`probe_platform_completion.py` 现在每行写
