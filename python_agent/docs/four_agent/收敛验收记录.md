## 9. 追加验收：单链路（业务状态先行 / Agent 单入口）

这一节回答一个具体问题：**同一个 `thread_id` 连续走完整个生命周期，会不会出现"两条答复、
两张工单、新问题被旧 Agent 接走"**。四步改造的落点：

| 步 | 文件 | 改成了什么 |
|---|---|---|
| 1 | `python_business/business/chat/routing.py`（新） | 纯函数 `route_message(msg_type, handling, pending, handoff)`：`human → media → handoff → pending → agent`，业务状态先判，判完才轮到 Agent |
| 1 | `python_business/business/chat/worker.py` | 按上面五分派执行；`pending` 分支只回"已提交，等待人工接入"，**不发起 Agent 请求**；`has_pending_ticket` 不再是选择旧 Agent 的开关 |
| 2 | `python_agent/app/api/chat.py` | 删除 `_legacy_json_impl()` / `_legacy_stream()`；`/agent/chat`、`/agent/chat/stream`、`/agent/chat/v2` 全部先过同一闸门；旧图只能经 `/agent/resume` |
| 3 | `python_business/business/chat/worker.py` | `AgentGateError`：`approval_pending → 建单/复用单 + /agent/resume + 本轮提交为 ticket`；`approval_state_unknown → 可重试基础设施错误`；**不再当 Agent 故障重试三次** |
| 4 | `python_agent/app/agent/legacy_approval/approval.py` | `ApprovalState.PENDING / CLEAR / UNKNOWN`；`aget_tuple` 抛异常 → `UNKNOWN`（不是 `CLEAR`）；`has_unfinished_approval` / `resume_approval` 遇 `UNKNOWN` 抛 `ApprovalStateUnknown` |

### 9.1 八步演练（`tests/test_thread_drill.py::test_same_thread_walks_the_whole_lifecycle`）

跑法：真 uvicorn 后台线程 + Worker 的**真代码**走真 TCP；只把工单台账（`FakeDesk`）与
检查点后端（`DrillSaver`，可切"探测失败"）换成替身。

| 步 | 场景 | 实测判据 |
|---|---|---|
| 1 | 普通问答「退货期限是多久？」 | `t1` 恰 1 条答复、工单 0 张、`/agent/chat/stream` 命中 1 次、没有 `get_tenant_agent` 调用 |
| 2 | 主动转人工「转人工」 | `t2` 恰 1 条答复、有效工单 1 张、**流式请求数不增**（不问 Agent） |
| 3 | 排队期间发新消息「还在吗？」 | `t3` 答复含「等待人工接入」、仍 1 张工单、请求数不增 |
| 4 | 人工接管后发消息 | `t4` `result_type=human`、仍 1 张工单、请求数不增 |
| 5 | 关闭工单后继续 AI | `t5` `result_type=ai`、有效工单归零、请求数 +1、无旧 Agent 调用 |
| 6 | 旧审批恢复（先造真 `interrupt`） | 新提问 → Agent 409 → Worker 建单 + `/agent/resume`（工单号与 resume 参数一致）→ 本轮 `result_type=ticket`；流式请求数 +1（证明 409 是真实往返）；`approval_state` 转 `CLEAR` |
| 7 | 检查点短暂故障 | Worker 拿到 503：**不建单、不写答复**，`record_failure` 收到 `approval_state_unknown` |
| 8 | Worker 重试（同一 `turn_id`，`attempt=2`） | `t7` 恰 1 条答复（重试不产生第二条）、旧 Agent 仍只被 resume 触达 1 次 |

收尾核对：七个 `turn_id` 每个恰好 1 条最终答复；工单总数 2 张（一次人工升级 + 一次旧审批各一张）、
工单号不复用、收尾时全部关闭；`/agent/chat`（JSON 分支）计数为 0。

### 9.2 这一项能不能被"糊过去"

替身只替换了**业务台账**与**检查点后端**，Agent 侧走的是 `app/api/chat.py` 的真路由与
`support_runtime` 的真执行体；`DrillSaver` 必须继承 `InMemorySaver`（LangGraph 在
`compile()` 时做 isinstance 校验，纯代理对象会被拒）。此外还有两道源码级闸门：

* `test_four_agent_api.py::test_production_entry_never_calls_the_legacy_agent`：
  `app/api/chat.py` 里不得出现旧图调用符号；
* `test_supervisor_contract.py::EntryParityTest`：`/agent/chat` 与 `/agent/chat/v2`
  对同一 `thread_id` 返回**同样**的 409 结构。

### 9.3 恢复闭环（第二轮补的四项）

第一轮只做到"新提问不进旧图"。审查发现恢复侧仍有四个洞，这一轮一次补齐：

| 优先级 | 洞 | 改法 |
|---|---|---|
| P0 | `agent_resume()` 只看 `content`，`success=false` / 503 / 超时都被当成"已恢复" | `business/chat/recovery.py::ResumeOutcome` 四态（`recovered` / `clear` / `unknown` / `unavailable`）；超时后**复查**再决定，不盲重试 |
| P0 | 恢复失败静默结案（Worker `_finish_ticket` 与同步 `_open_ticket` 都只 warn） | 失败写成工单待办 `approval_resume_state=1`（含 `attempts` / `next_at` / `error`），推 `approval_recovery` 给管理员，后台线程继续 |
| P0 | `ROUTE_HANDOFF` 在闸门前返回，建单却不 resume | 转人工分支也走 `check_approval=True`：先探测，pending 才恢复 |
| P0 | 排队期间再也走不到 Agent 的 409，"下次发消息自动好"不成立 | `recover_due()` 常驻 `chat.worker.run_loop`（默认 15s），只认数据库待办，与客户消息无关 |
| P1 | 失去租约仍会建单/resume；超时后可能对已恢复的审批再调一次 | `turns.lease_held()` 前置校验；恢复前先探测（已 `clear` 直接结案）；`SKIP LOCKED` + 短租约 + `attempts` 上限 |
| P1 | 生产缺 checkpointer 时被判成 `clear` 放行 | `app.state.require_checkpointer`（有 DSN 即真）+ `AGENT_REQUIRE_CHECKPOINTER`；缺 saver → `unknown`（503） |
| P1 | `/ws/chat` 的 409 被 `raise_for_status` 变成"调用agent失败" | `_gate_reply()` 处理 409/503；`/ws/chat`、`/api/user/chat`、Worker 共用同一套恢复函数 |

新增的验收场景（`tests/test_thread_drill.py` 5 项 + `python_business/tests/test_approval_recovery.py` 17 项 +
`test_stage33_contract.py` 3 项 + `test_realtime_cutover.py` 2 项）：

| 场景 | 判据 |
|---|---|
| 旧审批未完成时客户直接说"转人工" | 建单后旧审批被恢复，检查点 `CLEAR`，工单待办 `done` |
| resume 返回 `success=false`（`no_pending_approval`） | 判 `clear` 而非 `recovered`；`content` 为空也不算成功 |
| resume 返回 503 / 500 / 超时 / 连接失败 | `unknown` / `unavailable`，都落待办，不当作已恢复 |
| "服务端已恢复、客户端超时" | 复查到 `clear` 直接结案：`verified_after_failure=true`，**只发生一次 resume** |
| 失去租约的 Worker 继续运行 | 不建单、不 resume、不提交答复，也不计失败 |
| 排队工单存在但审批仍未恢复 | 客户只拿等待提示（不再问 Agent）；后台重试把检查点恢复成 `CLEAR`，客户不再收到第二条消息 |
| 人工接管 / 取消工单 | 接管：探测 `clear` 时不调 resume；取消：恢复失败仍返回 200（状态已改），落待办 |
| 容器重启后后台恢复 | `run_loop` 第一圈就跑 `recover_due()`；待办在数据库里，不依赖内存状态 |
