# 客服 Agent 合并目标（2026-10-18）

## 主项目与边界

以 `ai_customer_service` 的 Nginx → Go → Python Agent 为唯一用户入口。Go 负责用户令牌、租户、会话、MySQL 订单与工单；Python 负责受租户约束的 FAQ/RAG 与对话编排；Qdrant 和 PostgreSQL 继续分别保存该项目的知识库向量和会话检查点。`support-agent` 保留为能力来源与对照，不直接部署第二套 Streamlit/FastAPI/Milvus/Redis 数据平面，也不复制其 SQLite 演示订单/退款。

已保护基线：主项目 Git HEAD `5bac455bfebaac5b3fa171f3eea165190a84e5a7`，未跟踪 `.idea/`；来源项目 Git HEAD `860a29ff80f6e9b866e4cf1098c042e0da425f24`，包含未提交文件的快照见 `support-agent/runtime/merge-safeguard-20261018/`。合并前不改原有卷，不执行 `docker compose down -v`。

## 分阶段验收

1. **统一身份和入口**：浏览器只调用主项目 `/api/user/chat` 或 `/ws/chat`；Go 验证令牌和 `{tenant_id}:{user_id}` 会话标识，向 Agent 传递可信租户与会话。跨租户访问、无效身份拒绝。主项目消息和工单是会话事实来源。
2. **FAQ 与知识库**：将来源项目的回答边界、来源标识、未知时拒答等可迁移能力接进主项目的 `search_kb`；店铺政策只能来自当前租户审核的知识。来源项目的公开话术模板只能作参考，不得当店铺承诺。用当前 Qdrant/文档管理链路验收命中、未命中、租户隔离和知识库不可用。
3. **订单与转人工**：订单查询只读，必须在 Go 层按可信租户和客户归属检查后读取真实业务记录；不存在归属映射或外部真实订单接口时返回“无法核验”，不能用演示订单冒充真实订单。转人工复用主项目工单、后台接管和会话归档，并实测工单号与状态。
4. **前后端与回归**：实际从主项目聊天页面发起 FAQ、订单查询和转人工，核对 Go/Python/DB 结果及失败分支；通过相关 Go/Python 测试，记录命令、结果、限制。

## 写入操作门禁

退款和支付默认关闭。只有订单归属校验、真实业务接口、独立审批流及幂等/审计均打通并通过端到端验收后，才能单独开启。当前合并不得把 `support-agent` 的 SQLite 演示支付/退款工具暴露给用户。

## 完成判据与简历边界

每阶段以代码、测试和实际前端到后端证据为准；未接通的真实业务接口写明阻塞，不把模拟数据称为真实订单。简历只描述本人实际完成且可复现的客服 Agent 优化，区分原项目已有能力与本次新增能力，不声称拥有原项目整体架构或未经验证的性能/效果。
