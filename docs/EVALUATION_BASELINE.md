## 可复现输入与命令

- 规则标注：`python_agent/evaluation/gold_rules.jsonl`（11 条）；运行 `python -m evaluation.collect_rules evaluation/gold_rules.jsonl --output evaluation/rules_after.jsonl`，再运行 `python -m evaluation.score evaluation/gold_rules.jsonl --predictions evaluation/rules_after.jsonl`。
- 检索标注：`python_agent/evaluation/gold_retrieval.jsonl`（9 条）。在含演示 Qdrant 与模型配置的 Agent 容器内运行 `python -m evaluation.collect_retrieval evaluation/gold_retrieval.jsonl --output evaluation/retrieval_scored.jsonl`，再用 `evaluation.score` 汇总。此步骤只读 Qdrant，不创建会话。
- 原始预测和 JSON 报告保存在 `python_agent/evaluation/`。模型、知识库、集合或文档内容变化后应重新采集，不能跨版本直接比较绝对分数。

## 真实检索基线（演示租户 `t_demo`）

当前集合只有 **2 个源文档、9 个向量片段**，检索器取前 3 条。黄金集 7 条有答案、2 条无答案。按源文档 ID 去重后：有答案题的 Recall@3 = **7/7**，MRR = **1.0**；无答案题正确拒检 = **0/2**。两条无答案问题依然返回相似片段，说明“总取前 3 条”不能作为有答案的证据。

这次 9 次检索的客户端观测延迟 P50 = **156.67 ms**、P95 = **183.62 ms**，包含问题向量编码和 Qdrant 查询，不包含模型生成与前后端传输。样本过小，不能作为容量或 SLA 结论。

有答案题最高相关度最低为 **0.7665**，无答案题最高相关度最高为 **0.7151**。在这 9 条上，0.74 可把两组分开；**暂不把 0.74 设置成线上通用阈值**。需要扩充中文近义、难负例、跨行业和不同租户语料，标定不同 embedding/集合的阈值后再改检索器。当前片段没有稳定的分片 ID，因此本轮只评源文档命中；要评“正确条款是否进入上下文”，需要索引时保存稳定 chunk ID。

## 前后端实际答复抽查

通过演示访客登录，从统一网关对“未拆封能退吗？”和“已经拆封能退吗？”各发起一次咨询。修复后两者都进入政策专职 Agent，旧的“系统无法查询订单”错误表述在这 2 次回复中均未出现；两次回答也区分了拆封条件。**仍有残留问题**：回答会提“知识库”，且对商品类别未知的顾客使用“通常可以申请”“质量问题可以要求退换”等较强措辞。这两例不能判为答案忠实度通过；后续应增加商品类别、政策适用范围与人工审核的逐断言复核，并在必要时采用确定性安全答复。

## 下一轮验收门槛

1. 扩充至至少 100 条经人工确认的检索题，其中无答案和条件相反的问题分别不少于 20 条；记录每个租户的知识库版本、embedding 模型与文档 ID。选择阈值时同时报告有答案召回与无答案误命中，不能只优化其中一个。
2. 抽取至少 50 条真实或脱敏的复合问答，逐条核对订单事实、店铺条款、适用商品类别、缺失条件和禁止承诺。自动规则检查只验证明确字符串；**答案忠实度仍待双人标注或经校准的评判模型评估**。
3. 使用真实前端链路分开统计访客 FAQ、本人订单、跨客户拒绝、复合问答、转人工；每组记录成功率、P50/P95、模型空答及兜底率。性能优化只比较同一硬件、模型、知识库和并发配置下的前后数据。
4. 在 CI 固定运行单测、131 路由契约、11 条纯规则黄金集；外部模型与 Qdrant 的评测放在单独的验收任务，不把不稳定网络调用设为每次提交的阻断条件。
## 扩展复核：24 条检索题（同日）

在原 9 条之外加入货到付款、分期、退货地址、数字课程等难负例，固定集现为 12 条有答案、12 条无答案。运行 `evaluation/collect_retrieval.py` 后，原始结果在 `python_agent/evaluation/retrieval_24_scored.jsonl`，汇总在 `retrieval_24_report.json`。这是一轮**评测集扩容**，没有更改线上检索策略，不能写成检索质量的前后提升。

| 指标 | 9 条初测 | 24 条扩展复核 | 解读 |
|---|---:|---:|---|
| 有答案题源文档 Recall@3 | 7/7 | 12/12 | 仅两个源文档，按文档 ID 计；同一文档的错误条款仍会算命中 |
| 有答案题源文档 MRR | 1.0 | 1.0 | 同上，不能替代条款级评估 |
| 无答案题正确拒检 | 0/2 | 0/12 | 原始 top-3 检索必返回片段；下游模型是否拒答须另测 |
| 检索延迟 P50 / P95 | 156.67 / 183.62 ms | 155.51 / 169.34 ms | 仅问题编码＋Qdrant，样本和顺序不同，不能解读为性能提升 |

初测建议的 0.74 阈值被扩展集反例推翻：有答案的“能开增值税专用发票吗”最高分 0.6967；无答案的“退货地址和收件人电话是什么”最高分 0.7584。若仅按最高分拒检，0.74 在这组题上保留 11/12 有答案题、正确拒绝 11/12 无答案题。0.76 可拒绝 12/12 无答案题，却仍错拒上述有答案题；**本轮未上线任何阈值**。应先补条款级标注、商品及政策适用范围，并对近义难负例评估，再研究重排或证据充分性判断。

## 网关真实答复：7 条定向抽查

通过演示访客与 buyer1 客户令牌调用统一网关，记录在 `python_agent/evaluation/answers_live.jsonl`，报告在 `answers_live_report.json`。7 次 HTTP 与业务响应均成功；完整问答客户端延迟 P50 **7973.79 ms**、P95 **9920.15 ms**。这不是与检索延迟同一口径，也没有相同条件下的优化前基线，不能计算端到端性能提升。

简单必含／禁含字符串规则通过 6/7。唯一失败“未拆封能退吗”是**规则误报**：禁含“一定能退”命中了“不能只凭这一点就断定一定能退”。所以 6/7 既不是正确率，也不是忠实度。逐例人工检查还发现：

- 货到付款答复说“没有查询店铺政策或交易设置的能力”。Agent 实际有 `search_kb` 工具；缺少货到付款条款应表述为“现有店铺资料未说明是否支持”，这是能力表述错误。
- 包邮和专票答复列出了演示政策数字，同时拒绝将其当作真实店铺承诺。谨慎边界是对的，但两条均较长，且对演示店铺用户的直接可用性不足。
- 数字课程、未拆封、已拆封三条没有直接承诺退货资格，但提到了“知识库／检索／演示文档”，部分句子引用了未证实的通用类目规则，需要条款适用性逐断言复核。
- 复合订单问题正确返回本人演示订单 `ORD-2024-003` 的“待发货”，并提醒数字课程不能套用实物吊牌条款；回答没有输出原始检索片段。

这 7 条是定向样本，不能推断总体忠实度。**下一步优先修复能力误述、简化面向客户的政策答复，再用同一批输入复测**；忠实度需记录每个可核查断言对应的具体片段及适用范围，并由人工复核。当前检索评测只有源文档 ID，暂时无法给出可信的条款级忠实度数值。
## 修复与复测（同日后续）

上述第一版 7 条网关抽查使用同一个访客令牌连续提问，后续答案受到前文影响，**不能作为独立题评测**。`evaluation/collect_answers_live.py` 现为每条样本重新登录并创建会话；多轮对话需另设专门用例。旧的 `answers_live.jsonl` 和 `answers_live_after.jsonl` 保留作排障记录，不与独立题结果做性能对比。

修复了“支持货到付款吗”被路由到无检索工具的接待 Agent 的问题：支付方式咨询现在交给 FAQ 专职 Agent；“帮我付款”仍走人工受控分支。每个来自标题含“演示／示例”的检索片段在提供给模型前加来源标记；演示租户的 FAQ 最终答复由代码固定显示“仅供演示、不代表真实商家承诺”，而不是只依赖提示词。复合订单答复中的“知识库”术语改成顾客可读的“店铺资料”。这些是本轮实际代码改动；**没有上线检索分数阈值或宣称解决全部忠实度问题**。

独立会话结果在 `python_agent/evaluation/answers_live_isolated.jsonl` 与 `answers_live_isolated_report.json`；最后单独复测的复合订单答复在 `compound_verify.jsonl`。7/7 次 HTTP/业务响应成功，6/6 条 FAQ 均显示一次演示提示。货到付款答复改为“现有店铺资料没有明确说明”；专票答复未把示例政策当作本店正式承诺；本人订单 `ORD-2024-003` 状态仍为“待发货”，最终复合答复未展示“知识库”或原始片段。独立 7 题客户端延迟 P50 5.44 秒、P95 7.92 秒；由于会话方式、调用时序和模型随机性变化，**不能与第一版 7 题的 7.97/9.92 秒计算性能提升**。

修订了表面字符串规则：原“必须出现 99”会惩罚谨慎拒绝引用演示政策；原“一定不能退”会误命中“并不等于一定不能退”。现有 7/7 规则通过仅表示未触发这批有限字符串检查，**不是答案忠实度 100%**。本轮临时容器使用当前源码执行 **93 项 Agent 测试通过**，本地 Agent 健康；另从网关复测复合订单答复成功。

仍需补的产品能力：知识库文档应有机器可读的 `policy_status`（草稿／演示／商家已发布）、适用商品类别、有效期及稳定 chunk ID；仅已发布且适用的条款可用于肯定式店铺承诺。无答案检索在原始 Qdrant top-3 仍为 0/12 正确拒检，不能靠 0.74 单阈值修复；需要条款级标注、难负例和证据充分性判断。顾客答复仍偏长，且偶有“检索”等技术措辞，需进一步做可用性评测与简化。


## 知识库审核与证据门控最终验收（2026-10-23）

本阶段在 Python FastAPI 业务层、Agent、PostgreSQL、Qdrant 与 Vue 商家后台完成闭环。商家知识文档新增机器可读的 `policy_state`（待审核／演示／已发布／已停用）、`product_scope`（全部／实物／数字商品／未知）和生效、失效时间。**新上传文档默认待审核，不参与回答**；只有索引成功、已发布或明确标为演示、适用范围匹配且在有效期内的文档可进入回答。演示种子文档不能被重新标为真实商家承诺。FAQ 与订单＋政策复合任务使用同一套 PostgreSQL 权威状态检查；具体支付方式、地址、课程学习进度等条件必须在证据中出现，最终 FAQ 还会按用户原问题复核，防止模型把问题改写得过宽。

索引 worker 现在使用稳定分片 ID，先写入新分片并读回校验，再删除过时点；失败时不先删旧向量。商家后台可审核状态、适用范围和有效期。两个演示文档已安全重索引，Qdrant 当前 **9/9 个点带稳定 `chunk_id`**，旧的“订单接口尚未接通”表述为 **0 个点**。更新流程文档前保留了原件于 `backups/kb_process_c111e8bd_20261023.txt`，SHA-256 前 12 位为 `0B3B1F00A49C`。
